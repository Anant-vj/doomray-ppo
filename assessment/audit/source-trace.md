## Production inference path

1. The official worker loads `submission/agent.py`, resolves the device and instantiates `DoomAgent` with the declared observation and action spaces. The constructor requires action shape `(9,)`, limits PyTorch to one CPU thread, and loads the repository-relative `weights/policy.pt` with `weights_only=True`. The file selects `stack` memory. The resulting network enters eval mode and loads its state dictionary. Missing or incompatible weights fail at load. [Worker loader](D:/Doom/DevForge_DOOM/submission_artifacts/final-code-staging/env/doom_env/remote.py:340) · [Worker initialization](D:/Doom/DevForge_DOOM/submission_artifacts/final-code-staging/env/doom_env/remote.py:396) · [Agent load](D:/Doom/DevForge_DOOM/submission_artifacts/final-code-staging/submission/agent.py:11)
2. The official wrapper builds the per-decision observation with RGB, depth, player vitals, rays and visible entities. `pack()` reads the structured channels and prior action. Its 378 floats comprise 64 ray distances, 64 ray hit types, 160 entity features, 32 entity types, 32 masks and 26 context values. Context is 17 scaled vitals plus nine prior button bits. The policy reads neither screen pixels nor depth. [Observation contract](D:/Doom/DevForge_DOOM/submission_artifacts/final-code-staging/env/doom_env/spaces.py:73) · [Observation producer](D:/Doom/DevForge_DOOM/submission_artifacts/final-code-staging/env/doom_env/wrapper.py:169) · [Pack](D:/Doom/DevForge_DOOM/submission_artifacts/final-code-staging/submission/policy.py:20)
3. The encoder embeds ray hit types, applies a circular 1-D convolution, and pools the visible entity features under the entity mask. It fuses the ordered ray features, entity mean and maximum, and vitals/action context into 128 floats. The stack stores three 128-value encodings and appends the current one for a four-frame decision. [Encoder definitions](D:/Doom/DevForge_DOOM/submission_artifacts/final-code-staging/submission/policy.py:34) · [Forward encoder](D:/Doom/DevForge_DOOM/submission_artifacts/final-code-staging/submission/policy.py:51) · [History advance](D:/Doom/DevForge_DOOM/submission_artifacts/final-code-staging/submission/policy.py:61)
4. Six learned categorical heads split the actor's 15 logits into sizes `(3, 3, 3, 2, 2, 2)`. The first three choose forward/backward, left/right strafe and left/right turn, with a neutral choice for each pair. The last three choose ATTACK, USE and SELECT_NEXT_WEAPON. Sampling in eval mode remains stochastic. `buttons()` maps it to a nine-element `np.int8` vector. The agent stores the vector as next-step context and returns a copy. Its action calculation has no random-baseline or scripted fallback. [Head sampler](D:/Doom/DevForge_DOOM/submission_artifacts/final-code-staging/submission/policy.py:68) · [Button decoder](D:/Doom/DevForge_DOOM/submission_artifacts/final-code-staging/submission/policy.py:12) · [Agent action](D:/Doom/DevForge_DOOM/submission_artifacts/final-code-staging/submission/agent.py:30) · [Official order](D:/Doom/DevForge_DOOM/submission_artifacts/final-code-staging/env/doom_env/spaces.py:57)
5. The worker calls `agent.act(data)` for the next observation and the host validates the returned vector. The unchanged validator resets the game and worker at each map, requests one action per decision and passes it to `env.step(action)`. The wrapper checks shape and binary values and asks ViZDoom to hold those buttons for four engine tics. The agent's reset zeros its 384-value history and the nine prior button bits. [Worker reset and act](D:/Doom/DevForge_DOOM/submission_artifacts/final-code-staging/env/doom_env/remote.py:407) · [Host action validator](D:/Doom/DevForge_DOOM/submission_artifacts/final-code-staging/env/doom_env/remote.py:209) · [Official native loop](D:/Doom/DevForge_DOOM/submission_artifacts/final-code-staging/validate.py:399) · [Engine step](D:/Doom/DevForge_DOOM/submission_artifacts/final-code-staging/env/doom_env/wrapper.py:120) · [Agent reset](D:/Doom/DevForge_DOOM/submission_artifacts/final-code-staging/submission/agent.py:26)

The training rollout imports the same `Policy`, `pack()` and `buttons()`, then collects the actual environment step using those buttons. The trainer clears state on episode boundaries and saves the actual policy state dictionary with checkpoint metadata. The inference export keeps the memory type and policy weights. Training-only reward and engine telemetry stay outside the agent input. ## Independent offline inference probe

I loaded the exact C749 LFS bytes in the frozen CPU `DoomAgent`. The comparison
used the same architecture with the previous stack-397 inference weights
`a2a64cc8951434e13e10a76175fa87073f6edd0e3662ada380146e78ef785226` in a second
in-memory agent. The contract-valid synthetic inputs include two structured
observations and a pixel-only variant. No simulator or training process was
started by this check.

| History changed with the same C749 observation and prior buttons | 0.803297 |
| Prior buttons changed with the same C749 observation and history | 0.612438 |
| RGB and depth alone changed | 0 |

With seeds 2000–2031 applied identically after each reset, the weight swap
changed the sampled action in 28 of 32 paired draws. At seed 923, composing the
forward pass and decoder independently reproduced the actual agent action
`[0, 1, 1, 0, 1, 0, 0, 0, 0]`. Resetting and reseeding reproduced a four-action
sequence. All 216 head combinations decoded to distinct legal
`MultiBinary(9)` vectors. An in-memory override to an absent weight path raised
`FileNotFoundError`. An eight-button space raised `ValueError`.
